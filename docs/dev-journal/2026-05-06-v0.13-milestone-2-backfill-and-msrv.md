# v0.13 milestone 2: lazy backfill + MSRV bump

**Date:** 2026-05-06
**Version:** v0.13.0-beta.1

## Recap

Milestone 1 ([2026-05-06-v0.13-milestone-1-id-aware-upsert.md](2026-05-06-v0.13-milestone-1-id-aware-upsert.md))
added `remote_item_id` to `file_index` and routed the poller through
`upsert_remote_file_by_id_or_path`, so OneDrive `Modified`-with-new-
path renames update the existing row in place. But pre-v0.13 rows
have NULL `remote_item_id`, and a delta-only mount might never see a
full poll to backfill them — so they would still trip the v0.12.3
self-heal forever. Milestone 2 closes that gap.

## What changed

### Lazy backfill via the self-heal

`crates/stratosync-daemon/src/fuse/mod.rs::do_hydrate` already does a
verifying `stat()` whenever a download fails NotFound. When stat
succeeds, we now also pull the returned `item_id` (if any) and write
it onto the row via the new `StateDb::set_item_id_if_absent`. The
`IS NULL` guard on the UPDATE means we never overwrite an
authoritative ID with a possibly-stale stat result.

This gives every legacy row a "graduation moment": the first time the
band-aid fires for it, the row picks up an ID and joins the id-aware
upsert path. The *next* rename event for that item is handled in
place — no more band-aid loop.

### Why the band-aid stays

- Backends without stable IDs (WebDAV, raw S3) genuinely have no
  `item_id` to match on. They'll keep relying on path-based upsert
  and the band-aid for stale-row recovery indefinitely.
- Rows that haven't been touched since pre-v0.13 still need *something*
  to handle their first rename. The lazy backfill is exactly that
  something.

We can revisit removal once telemetry shows the path is rarely hit.

### MSRV bump to Rust 1.85

The dep pins from v0.11/v0.12 (`clap = "=4.5.57"`, `toml = "=0.7.2"`,
`toml_edit = "=0.19.9"`, `fuser = "0.14"`) all existed because of
Rust 1.80 compatibility. They're gone now:

- `clap = "4.5"`, `clap_complete = "4.5"` — picks up 4.6+ which needs
  `edition2024` (Rust 1.85).
- `toml = "0.8"`, `toml_edit = "0.22"` — picks up `indexmap` 2.x
  (needs Rust 1.82).
- `fuser = "0.15"` — its non-dev `clap` dep no longer collides with
  our exact-version pin (because we no longer have one). 0.15 also
  changed the `getattr` callback signature: it now receives an
  `Option<u64>` file handle. One-line adapter in `StratoFs::getattr`.

`install.sh` now requires Rust 1.85+; CLAUDE.md's Prerequisites and
"Dependency Pinning" sections were updated accordingly.

## Tests added

`crates/stratosync-core/src/state/mod.rs::state::tests`:
- `set_item_id_if_absent_fills_null_row`
- `set_item_id_if_absent_does_not_overwrite_existing` — proves the
  `IS NULL` guard prevents authoritative IDs from being clobbered

`crates/stratosync-daemon/src/fuse/mod.rs::hydrate_tests`:
- `do_hydrate_backfills_item_id_from_stat_on_recovery` — the
  end-to-end: legacy row (NULL ID) + failing download + succeeding
  stat → row keeps existing, AND the stat-returned `item_id` is now
  persisted in the row.

## What's still pending for v0.13.0 final

- ID-aware `RemoteChange::Deleted { path, item_id }` — currently
  match-by-path only. OneDrive doesn't actually emit Deleted for
  renames, so this is a robustness improvement, not a fix. Defer.
- Drop the `upsert_remote_file` / `upsert_remote_file_gen` wrappers
  entirely (currently kept as thin shims for back-compat with test
  fixtures). Low priority — they cost nothing.
- Real-world soak: confirm via `stratosync_mount_hydration_consecutive_failures`
  Prometheus gauge that the band-aid fires less and less over time as
  rows get IDs. If it stops firing entirely, we can remove it.
