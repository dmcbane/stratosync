# v0.13 milestone 3: id-aware delete events + soak signal

**Date:** 2026-05-06
**Version:** v0.13.0-beta.2

## Scope

Of the three open items from milestone 2's dev-journal, this milestone
deliberately does only one (item 3 — id-aware Deleted events) plus a
small log-enrichment to instrument the soak signal for the eventual
band-aid removal.

The other two were dropped on inspection:

- **Drop the v0.12.3 self-heal band-aid**: premature. We need
  Prometheus / journal data showing it fires near-zero times across
  real workloads first. This milestone makes that signal *visible*
  but doesn't act on it yet.
- **Drop the legacy `upsert_remote_file` / `_gen` wrappers**: low
  value. They cost nothing (already thin shims), and removing them
  would churn every test fixture for a purely cosmetic win.

## What changed

### `RemoteChange::Deleted { path, item_id: Option<String> }`

Previously path-only. Now carries the backend's stable ID alongside.
Both delta providers populate it: OneDrive from `OneDriveItem.id`,
Google Drive from `change.file_id` (or `file.id` for trashed). WebDAV
and any future no-ID backend pass `None` and the path fallback handles
them — fully back-compat.

The reason this matters: a delete event for a file whose `remote_path`
in our DB is stale (because a Modified-with-new-path arrived in the
same or a recent delta page) used to silently fail to match anything
under path-based lookup. With ID-based matching, we find the right row
regardless of which path the backend's delete event carried.

### `StateDb::delete_remote_entry_by_item_id`

Mirror of `delete_remote_entry_by_path` but matched on
`(mount_id, remote_item_id)`. Same dirty/uploading protection.
Returns `Some((inode, cache_path))` on success, `None` if no match.

### Poller delta-mode handler: id first, path fallback

```rust
let result = match item_id.as_deref() {
    Some(id) => match by_id { Some => take, None => fall to path },
    None => path,
};
```

The fall-through to path handles two cases: the row was indexed
pre-milestone-1 (no ID stored), and any future bug that drops the ID
from a delete event.

### Self-heal log enrichment

`do_hydrate`'s prune branch now reads the row's `remote_item_id` (via
new `StateDb::get_item_id`) and logs differently based on the result:

- **NULL id**: `"stale DB row (legacy null-id) — pruning; this is expected and tapers as IDs backfill"`. Soak telemetry: this rate should
  decline over time.
- **Known id**: `"stale DB row WITH known item_id pruned — id-aware
  upsert may have missed a delta event"`. Soak telemetry: this rate
  should be *near zero*. If it isn't, the upsert path is missing
  something — investigate before considering band-aid removal.

## What's still open for v0.13.0 final

- Soak the `dialog-warning`-flip rate and journal `stale DB row
  WITH known item_id` count across real workloads. If both stay near
  zero for, say, two weeks: drop the v0.12.3 band-aid in a future
  beta. If `WITH known item_id` is non-trivial: dig into which delta
  events the upsert path is missing.
- Cosmetic: drop `upsert_remote_file` / `_gen` wrappers (zero-impact,
  do whenever convenient).
