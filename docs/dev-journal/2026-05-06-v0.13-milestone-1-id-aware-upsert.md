# v0.13 milestone 1: ID-aware rename detection in the upsert path

**Date:** 2026-05-06
**Version:** v0.12.4

## Why this exists

v0.12.3 added a self-heal that pruned stale `remote_path` rows when
`do_hydrate` got a `NotFound` from the backend. That fixed the user-
visible "cp loops EAGAIN forever after a remote rename" symptom but
left the underlying cause in place: `StateDb::upsert_remote_file_gen`
matched on `(mount_id, remote_path)`, so OneDrive `Modified`-with-new-
path events for renames inserted a NEW row at the new path while the
OLD row sat in the DB pointing at a dead path. Dev-journal entry:
[2026-05-06-onedrive-delta-rename-stale-paths.md](2026-05-06-onedrive-delta-rename-stale-paths.md).

This milestone fixes the upsert path itself.

## What changed

1. **Schema (`migration 0008_remote_item_id.sql`)** — adds a nullable
   `remote_item_id TEXT` column to `file_index` plus a partial unique
   index `(mount_id, remote_item_id) WHERE remote_item_id IS NOT NULL`.
   Existing rows have NULL until they're touched by a fresh poll.

2. **`RemoteMetadata.item_id: Option<String>`** — the new field that
   carries the backend's stable identifier through the type system.
   Populated from:
   - `OneDriveItem.id` (made required at the deserializer level — it
     always exists in real Graph responses, just wasn't captured before)
   - `RcloneLsJsonEntry.id` (already existed, now also flows to
     `item_id` instead of only being a poor-man's etag fallback)
   - Google Drive's `GDriveFileMetadata.id`
   - WebDAV / mock backends pass `None`

3. **`StateDb::upsert_remote_file_by_id_or_path`** — replaces the
   path-only `upsert_remote_file_gen` (the legacy method stays in place
   for now to keep the diff small). Match order: item_id first, path
   second. Three behaviors:
   - **ID match, same path**: in-place update (etag/size/mtime).
   - **ID match, different path**: in-place rename — same inode, new
     `remote_path`/`parent`/`name`. Path collisions get evicted first
     (a `mv old new` overwriting an existing `new`).
   - **No ID match (or `item_id == None`)**: legacy path-based upsert,
     with the bonus that any row matched by path lazily backfills its
     ID from the new entry (so the second poll for any pre-v0.13 row
     starts working with rename detection automatically).

4. **Poller wired up** — both `poll_once` (rclone full poll) and
   `poll_once_delta` now call the new method. Full poll's generation
   sweep was already enough to catch stale rows for path-based
   renames; the change here is forward-compatible, populating IDs so a
   later switch to delta mode for that backend doesn't see NULLs.

## What this does NOT do (deferred to milestone 2)

- **Backfill of existing rows** — pre-v0.13 rows have NULL
  `remote_item_id`. They get IDs lazily as they're re-touched by
  polls, but a one-shot backfill via `backend.stat()` would speed
  this up. Until backfilled, those rows still rely on the v0.12.3
  self-heal for stale-path recovery.
- **Removing the v0.12.3 self-heal band-aid** — it's defense-in-depth
  for both NULL-ID rows and backends without a stable-ID concept. We
  can remove (or downgrade to a debug-log-only path) once everything
  is on the ID path.
- **Item-ID-aware deletes** — `RemoteChange::Deleted { path }` still
  matches by path. OneDrive doesn't actually emit Deleted for renames
  (that's the original bug), so this is fine in practice; a future
  change can make it `Deleted { path, item_id: Option<String> }` for
  robustness.

## Two non-obvious design choices

### Why both upsert methods coexist

I considered ripping out `upsert_remote_file_gen` entirely and routing
everything through the new method. Tempting (one less code path) but
risky for a v0.12.x patch — the legacy method is exercised by the
existing test suite in subtle ways. Keeping both lets the new path
prove itself in the next release cycle before we cut over and delete
the old one in v0.13.0-beta.

### Why the index is partial, not unconditional

`CREATE UNIQUE INDEX ... WHERE remote_item_id IS NOT NULL` lets pre-
v0.13 rows (and rows from no-ID backends) coexist without artificial
collision concerns. The non-partial alternative would have required a
synthetic ID for every row, which is more code, more surface area for
bugs, and meaningless for backends like WebDAV that genuinely have no
stable identifier.
